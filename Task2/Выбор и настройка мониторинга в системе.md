## Мотивация
В качестве основных факторов внедрения мониторинга я бы выделил:
- оперативное реагирование на возникающие проблемы в системе - они будут выявляться, а возможно и решаться еще до того, как начнут жаловаться пользователи
- в целом у нас появится виденье, что происходит в системе
- позволит проанализировать текущее состояние системы - например эффективно ли используются ресурсы, достаточно ли их и тд
- позволит выявить узкие места в системе и поможет запланировать дальнейшие улучшения
- сбор и анализ различных бизнес-метрик позволит бизнесу лучше понимать текущее положение компании, а так же более эффективно планировать дальнейшее развитие продукта 

## Выбор подхода к мониторингу
### Shop API: 4 золотых сигнала
**Задержка**:
- Response time (latency) - время выполнения запроса. Будем использовать лейблы для http кода статуса, http метода и uri

**Трафик**:
- Number of requests (RPS) per user - количество запросов выполняемых пользователем в сек. Будем использовать лейблы для http кода статуса, http метода, uri и логин пользователя
- Number of requests (RPS) - количество запросов выполняемых в сек. Основа предыдущая метрика, просто в фильтрах не используем лейбл логин пользователя

**Ошибки**
- Number of HTTP 500 - количество запросов завершившихся 5xx статусом. Переиспользуем выше указанные метрики, фильтруемся по коду статуса

**Насыщенность**
- CPU % - использование процессора
- Memory Utilisation - использование RAM
- JVM Memory Usage - использование памяти JVM. В лейблах разбивка по различным областям памяти - стек, heap (с разбивкой по поколениям), metaspace
- GC activity - активность Garbage Collector

### Бизнес-метрики
Бизнес-метрики вынесены в отдельный дашборд, тк они по факту общие на всю систему. Например, статусы заказа могут меняться в разных частях системы. На данный момент критичными для нас выглядят следующие:
- Count of orders in intermediate statuses exceeding the time threshold - заказы, которые находятся в промежуточном статусе дольше порогового значения.
В лейблах будет статус заказа, и время (в днях) которое заказ находится в данном статусе. Для разных статусов будут определены собственные пороговые значения.
- Order status changing time - время переходов между статусами, будем отслеживать различные перцентили. После сбора статистики можно будет установить пороговые значения для различных переходов, превышение которых будет приводить к алертам
- Price calculating time - время расчета стоимости заказа
