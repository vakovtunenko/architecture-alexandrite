## Кандидаты на трассировку
- Бекенд-сервисы: Shop API, CRM API, MES API - они по большей части являются точками входа в систему и мы сможем отследить весь путь запроса и идентифицировать проблемы с производительностью
- БД: Shop DB, MES DB - трассировка запросов к БД позволит выявить проблемные sql
- Очередь: RabbitMQ - тк именно через нее происходит синхронизация статусов и большая часть подозрений на проблемы с зависаниями заказов падает на нее 
- Хранилище файлов: S3 - загрузка и чтение файлов потенциально тоже может быть узким местом производительности
- Фронтенд приложения: Internet Shop, CRM, MES - позволит отслеживать пользовательский путь, а так же выявить потенциальные неоптимальные использования API бекенда

Список данных для трассировки:
- идентификатор трейса
- идентификатор спана
- идентификатор дочернего спана
- имя операции
- различные временные показатели - начало, конец, сколько выполнялось
- информация о системе - хост, имя сервиса и тп
- в случае ошибок стек трейс
- можно добавить идентификатор пользователя если он есть
- для sql запросов можно записывать сам запрос
- для очередей как минимум имя очереди
- для http запросов соответствующие показатели - код ответа, метод, путь и тд
- для S3 набор специфичных для нее данных - бакет, ендпойнт и тд

## Мотивация
Я бы выделил следующие факторы внедрения трассировки:
- Наблюдаемость, диагностика и помощь в разборе инцидентов - благодаря трассировке у нас будет представление как происходит взаимодействие в системе, где возникают проблемные места, что позволит нам оперативнее разбирать возникающих инцидентов
- Производительность и оптимизация - сразу увидим где проседает производительность и что нужно оптимизировать
- Дерево зависимостей - мы будем знать как компоненты взаимодействуют друг с другом, что особенно важно для больших систем
- Дополнительный разрез статистики - помимо метрик, благодаря трассировке у нас будет статистика под другим углом

Влияние на метрики:
- Трассировка будем иметь прямую корреляцию с такими техническими метриками, как количество выполняемых запросов, response time и тп
- А так же и бизнес метрики тоже - где заказы потерялись, почему статусы зависли и тп

То есть как было упомянуто выше - это еще один срез статистики, который будет дополнять метрики и позволит нам получить более полную и детальную картину происходящего

## Предлагаемое решение
Для трассировки мы будем использовать OpenTelemetry и Jaeger - Jaeger клиенты задеприцированы и само комьюнити Jaeger в документации рекомендует использовать OpenTelemetry SDK - backend Jaeger с версии v1.35 поддерживает данные из OpenTelemetry SDK из коробки

Да и поддерживаемый стек у jaeger клиентов достаточно ограниченный, выбор OpenTelemetry SDK гораздо богаче под большее количество технологий 

То есть в качестве основной платформы трассировки у нас будет использоваться Jaeger, а экспорт из приложений будет с использованием OpenTelemetry SDK

Верхнеуровневый список работ для внедрения трассировки:
- в качестве хранилища будем использовать Elasticsearch тк он же нам понадобится и для логирования, нужно будет его настроить и развернуть если это еще не было сделано при настройке логов
- внедрить и настроить в приложениях соответствующие OpenTelemetry SDK
- настроить и развернуть jaeger-collector
- настроить и развернуть jaeger-query и ui

## Компромиссы
В качестве компромиссов я бы выделил следующее:
- трассировка фронтенд приложений не является первой необходимостью и в данный момент скорее всего не принесет особой пользы, тк описанные проблемы указывают, что они находятся где-то на бекенде
- внедрение трассировки S3 может вызвать сложности да и по началу мы можем обойтись и без нее, если и есть какие-то проблемы с производительностью S3 - в целом косвенно мы сможем это понять по общему трейсу
- настройка трассировки для БД тоже может быть не такой простой, а насколько я знаю OpenTelemetry SDK для того же Spring Boot из коробки умеет делать отдельные спаны при выполнении SQL запросов из самого приложения, для начала нам этого будет достаточно

## Аспекты безопасности
- все компоненты трассировки не будут доступны из внешней сети, только из внутренней
- доступ к UI будет только у сотрудников технической поддержки, а так же у разработчиков
- чувствительные данные не будут попадать в трассировку, в случае необходимости будет настроена фильтрация таких данных для их исключения
