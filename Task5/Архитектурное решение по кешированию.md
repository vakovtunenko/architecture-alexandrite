## Мотивация
- кеширование поможет снизить проблемы с производительностью за счет кеширования результатов обращения к БД и сложных вычислений (например, расчет стоимости изготовления украшения)
- ускорение response time и отклика системы - за счет уменьшения обращений к БД пользователи будут получать данные гораздо быстрее
- поможет лучше переживать пиковые нагрузки, тк не будет постоянного обращения к БД

Кеширование поможет решить следующие проблемы:
- долгая загрузка страниц - кеширование поможет избежать постоянного обращения к БД, а значит страницы будут грузиться быстрее (например, страница с заказами)
- задержки в обработке заказов - кеширование результатов расчета стоимости улучшит опыт пользователей как приложения, так и API
- в целом станет меньше проблем с производительностью - кеширование различных данных, например таких как список товаров снизит нагрузку на систему, а пользователи будут быстрее получать свои данные
- так же повышается надежность системы, тк при пиковых нагрузках вероятность отказа системы из-за долгих и частых обращений к БД уменьшается
- помимо этого кеширование данных на стороне клиента так же снижает нагрузку на саму систему в разрезе передачи данных - меньше данных гуляет по системе, меньше нагрузка на сеть, меньше вероятность забить пропускную способность сети

Что планируем кешировать:
- непосредственно детальную информацию по заказам (для SHOP API, CRM API, MES API)
- для улучшения производительности дашбордов с заказами для операторов - если для них первоочередной потребностью является возможность видеть самые новые заказы со статусом готовым к работе - то акцент делать на результатах такой выборки (MES API)
- результаты сложных и промежуточных вычислений стоимости украшения для MES API
- так же кешировать можно и список товаров для SHOP API

## Предлагаемое решение
Для разного функционала будет использоваться различное кеширование:
- **информация по заказам - серверное кеширование**
  - необходимо централизованное управление кешированием (заказы могут меняться в разных частях системы, а клиентских приложения у нас три)
  - заказы могут содержать чувствительную информацию и кешировать ее на клиенте кажется не безопасным
  - чтобы пользователи получали актуальную информацию по заказу, легче управлять этим на стороне сервера
  - будем использовать Cache-Aside, основные аргументы - гибкий контроль над управлением кешем, модель заказа не совпадает с моделью данных (собираем из нескольких таблиц, что-то преобразуем и тп), чтений сильно больше, чем записей
  - заказы не настолько часто изменяются, поэтому и Refresh-Ahead (излишняя частота обращения к БД) и Write-Through (излишнее усложнение и задержки при записи) с Write-Behind (может привести к неконсистентности данных в случае сбоя, что не приемлемо) и Read-Through (модель в коде и модель данных отличается, нет компетенций на реализацию) выглядят не подходящими
- **дашборд с заказами для операторов - серверное кеширование**
  - серверное кеширование позволит централизованно управлять данными
  - к данному дашборду может обращаться большое число операторов одновременно, поэтому серверное кеширование позволит снизить нагрузку на БД
  - операторы работают только с определенными статусами заказов, поэтому данный дашборд не будет слишком часто изменяться, но актуальность его критична, поэтому клиентское кеширование не подходит
  - будем использовать Cache-Aside, основные аргументы - может быть реализован силами разработки и будет гибкий контроль над управлением кешем, модель для поиска не совпадает с моделью данных
  - не будем использовать Refresh-Ahead (излишняя частота обращения к БД), Read-Through (модель в коде и модель данных отличается, нет компетенций на реализацию), Write-Through и Write-Behind (оптимизируем чтение)
- **результаты сложных вычислений стоимости украшения - серверное кеширование**
  - кеширование результатов вычисления на сервере позволит переиспользовать их при запросах из разных систем
  - так же не исключено кеширование промежуточных вычислений, чтобы не проводить вычисление полностью с нуля, если 3d модель была немного изменена
  - в целом описание выше больше фантазия, тк не понятно как вообще выполняются такие вычисления 
  - будем использовать Cache-Aside - позволит гибко управлять кешированием, тк оно может зависеть от множества факторов (так же не забываем про кеширование промежуточных вычислений, которые можно переиспользовать и тп)
  - не будем использовать Refresh-Ahead (избыточно, результаты вряд ли будут часто пересчитываться), Read-Through (нам нужно управлять логикой кеширования на уровне кода), Write-Through и Write-Behind (оптимизируем чтение)
- **список товаров - клиентское кеширование**
  - выбор в пользу клиентского кеширования потому что эти данные обновляются достаточно редко, а пользователь скорее всего часто будет ходить по страницам туда-сюда и часто обновлять список товаров, таким образом мы сможем уменьшить нагрузку на сервер
  - так же уменьшим количество данных передаваемых по сети, тк список товаров явно будет занимать больше места, чем например информация по одному заказу
  - и быстрый отклик системы повысит пользовательский опыт и вероятность того, что пользователь может задержаться в магазине для его изучения и в итоге что-нибудь приобрести

### Инвалидация кеша
- **информация по заказам**
  - будем использовать комбинированный подход - TTL + при изменении заказа по ключу (по факту это комбинация программного, при любом изменении и по ключу)
    - заказы меняются не слишком часто, и не всегда есть необходимость держать заказ в кеше постоянно, поэтому будем инвалидировать кеш по TTL
    - в то же время тот же статус заказа может меняться в различных частях системы, к тому же будет странно, если пользователь сам своими руками меняет статус заказа, но изменений после этого он не видит, поэтому кеш будет инвалидироваться так же при изменениях, но по ключу, чтобы инвалидировалась только та запись, которая была изменена
  - инвалидация, основанная на запросах пользователя не подходит, потому что данные могут меняться разными пользователями из разных частей системы
- **дашборд с заказами для операторов**
  - будем использовать инвалидацию при изменении тк нам важна актуальность данных на дашборде
  - тк нам важна актуальность данных, то TTL и привязка к запросам пользователя не подойдет, помимо этого это рабочий дашборд, заказы должны быть взяты в работу, поэтому нужды в TTL нет
- **результаты сложных вычислений стоимости украшения**
  - будем использовать программную инвалидацию, тк у нас есть логика кеширования промежуточных вычислений и нужно будет инвалидировать кеш при определенных условиях
  - так же дополнительно можно использовать TTL, чтобы данные не хранились слишком долго
  - инвалидация при изменениях и запросах пользователей выглядит избыточной, тк вряд ли она будет изменяться слишком часто, к тому же далеко не факт, что она изменится при изменении 3d модели (дело в логике расчета), в любом случае всем этим мы будем управлять программно
- **список товаров**
  - для реализации клиентского кеширования будем использовать заголовок Cache-control
  - не смотря на то, что данные по товарам изменяются редко, все же чтобы избежать конфузов, когда цена изменилась, а у пользователя данные закешированы и его потом ждет сюрприз, использовать TTL не будем
  - вместо этого будем использовать значение no-cache для Cache-control, и затем клиентское приложение будет отправлять условный запрос с заголовком If-None-Match для проверки, изменились ли данные
